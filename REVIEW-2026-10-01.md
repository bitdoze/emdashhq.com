# EmDash HQ review, 1 October 2026

The navigation delay is reproducible on the production site. Requests that miss the Cloudflare HTML cache took 1.47–2.46 seconds to first byte. Immediate repeats took 70–112 ms. The existing hover prefetch works; changing its strategy is not needed to investigate or address these findings.

This review changed no application code, CMS content, deployment settings, or preload behavior. It covers the project source, local Site Scripts plugin, seed/schema, installed EmDash and Cloudflare implementation, production HTTP responses, browser behavior, build, types, and dependency advisories. Authenticated editing and destructive security tests were outside the checks performed.

Implementation and deployment were performed afterward. See [the fix record](FIXES-2026-10-01.md) and [the categorized performance guide](emdash-perf-best-practices.md) for current status; the measurements below describe the original review.

## Findings

Priorities: P1 materially affects visitors, content correctness, accessibility, or indexing; P2 is a functional or performance improvement; P3 is a smaller issue. There are five P1 findings, nine P2 findings, and one P3 finding. No P0 blocker was observed.

### 1. P1: Cache misses expose substantial CMS and database latency

**Locations:** [astro.config.mjs](/home/dragos/projects/emdashhq/astro.config.mjs:17), [Base.astro](/home/dragos/projects/emdashhq/src/layouts/Base.astro:22), [Site Scripts](/home/dragos/projects/emdashhq/plugins/site-scripts/src/index.ts:98).

The project enables Cloudflare HTML caching and KV object caching, but the latter deliberately does not serve query snapshots while an anonymous response is being generated for the route cache. This prevents a content purge from rebuilding HTML from stale KV data. That behavior is present in the installed EmDash implementation and documented in [EmDash object caching](https://docs.emdashcms.com/deployment/object-cache/).

The slow path therefore still initializes the CMS, loads the page, reads site settings and five menus, and invokes the plugin. Each menu requires a menu-row lookup and an item lookup. The layout already starts its six reads with `Promise.all`; the primary-menu read in Hero is also deduplicated by EmDash's request cache. Those are good practices, and simply adding another `Promise.all` or blaming the duplicate Hero call would be misleading.

Contact's 21 queries and 968 ms middleware time establish that list blocks are not the sole cause. The installed D1 adapter coalesces SELECTs, while physical calls on a shared D1 session are ordered. CMS initialization and dependent reads still have a cost.

**Recommendation:** profile and reduce the origin path, particularly cold initialization, menu loading, and plugin configuration reads. Record database statements and physical batch boundaries before choosing an upstream or site-level change. Retain safe route-cache fills and current hover behavior. A cache hit is already fast; focus on the miss path and reliable invalidation. Do not disable freshness safeguards just to make a benchmark faster.

### 2. P1: Four collection blocks omit cache dependencies

**Locations:** [SiteTutorials.astro](/home/dragos/projects/emdashhq/src/components/blocks/SiteTutorials.astro:19), [SiteVideos.astro](/home/dragos/projects/emdashhq/src/components/blocks/SiteVideos.astro:19), [SiteResources.astro](/home/dragos/projects/emdashhq/src/components/blocks/SiteResources.astro:20), [SiteServices.astro](/home/dragos/projects/emdashhq/src/components/blocks/SiteServices.astro:19).

These queries destructure only `entries`. Their returned `cacheHint` is discarded. The route registers the `pages` entry and the layout registers settings and menus, but nothing registers the tutorials, videos, resources, or services displayed by the blocks.

Publishing or changing a listed entry can therefore leave the homepage and listing HTML stale until expiry or a separate purge. Updating KV alone does not remove already cached HTML. The lists' modification dates are also omitted from conditional-response hints.

**Recommendation:** capture each result's `cacheHint` and call `Astro.cache.set(cacheHint)` when enabled. Apply this even when a collection is empty so adding its first entry can invalidate the empty page. This is the documented [content-query caching pattern](https://docs.emdashcms.com/guides/querying-content/).

### 3. P1: Database errors can become cacheable empty content or 404s

**Locations:** [page route](/home/dragos/projects/emdashhq/src/pages/[...slug].astro:14) and the four collection-query locations above.

EmDash distinguishes `error` from a legitimately missing entry or an empty collection. The project ignores `error` everywhere. A failed page query becomes a 404 for an ordinary page, or a welcome page for `/`. A failed collection query becomes “No tutorials published yet” or another empty state in a successful response.

The public route rules make these responses eligible for caching, turning a transient failure into a longer visible outage. Production testing confirmed that an ordinary missing-page 404 is cached, so the distinction matters.

**Recommendation:** inspect `error` before missing-content handling. For actual failures, log server-side details, return a useful 503 or 500 response, opt out of route caching, and set `Cache-Control: no-store`. Retain real 404s and honest empty states for successful queries.

### 4. P1: The sitemap advertises nonexistent page URLs

**Locations:** [pages collection definition](/home/dragos/projects/emdashhq/seed/seed.json:856), [page route](/home/dragos/projects/emdashhq/src/pages/[...slug].astro:8).

The live `/sitemap-pages.xml` lists all seven pages under `/pages/`, including `/pages/tutorials` and `/pages/home`. Both tested examples return 404. Actual routes are `/tutorials/`, `/videos/`, etc., with `home` mapped specially to `/`.

The pages collection does not specify a URL pattern, so EmDash uses its `/{collection}/{slug}` fallback. This is confirmed by [EmDash's sitemap documentation](https://docs.emdashcms.com/guides/seo/).

**Recommendation:** configure the pages collection's URL pattern to match the route, updating the existing database schema as well as the seed. Handle the special `home` mapping explicitly, through a custom sitemap route if needed. Merely changing a seed file is insufficient for an already configured production database. Ensure the sitemap includes `/`, and verify every advertised URL resolves to the intended canonical page.

### 5. P1: Primary-button text fails normal-text contrast in dark mode

**Locations:** [brand tokens](/home/dragos/projects/emdashhq/src/styles/theme.css:32), [button styling](/home/dragos/projects/emdashhq/src/styles/theme.css:356), [active filters](/home/dragos/projects/emdashhq/src/styles/theme.css:423).

White text remains white while the dark-mode background becomes bright blue. Chromium confirmed a primary-button gradient beginning at `rgb(59,130,246)` and ending near `rgb(51,154,244)`. White contrast is approximately 3.68:1 and 2.97:1 respectively. The labels are small text, requiring 4.5:1 under WCAG 1.4.3. Hover colors can be brighter still.

**Recommendation:** give dark-mode filled controls a darker background or dark text with sufficient contrast across the entire gradient. Verify ordinary, hover, and active-filter states. Body text and general theme switching behaved correctly in the checks.

### 6. P2: List queries overfetch and silently truncate “all”

**Locations:** the four collection blocks in finding 2.

Every block requests 100 entries before filtering and slicing. A homepage block displaying three entries still requests the first 100. Filtering resource kind, price, or featured status afterward can miss matching entries beyond that initial page. Services sort only the fetched subset, so an older service with a lower sort order may never appear.

The admin label “0 = all” is also inaccurate once a collection exceeds 100 entries because the result cursor is ignored.

**Recommendation:** move supported filters and ordering into the content query, request the needed limit for bounded blocks, and implement cursor pagination for complete listings. If “all” is intentionally capped, disclose that cap and provide navigation. Current seeded collections are small; this is a confirmed code limitation, not a claim that 100 records were downloaded in today's measurements.

### 7. P2: Shared styles are repeated in every HTML document

**Locations:** [build configuration](/home/dragos/projects/emdashhq/astro.config.mjs:26), [block imports](/home/dragos/projects/emdashhq/src/components/MarketingBlocks.astro:4).

`inlineStylesheets: "always"` embeds about 79,253 bytes of CSS on each checked content page. Around 69,695 bytes are the combined application/component stylesheet; the remainder describes fonts. Styles for all imported block types are present even when that page uses only a few of them.

The document sizes are roughly 100–125 KB decoded, though compression reduces the transmitted HTML to about 20–25 KB. The browser still transfers or validates a document, parses CSS, and builds styles on ordinary navigation. Public navigation does not download the large React admin bundles, so the build's large-chunk warning should not be treated as evidence that menu clicks load 8 MB of JavaScript.

**Recommendation:** allow sizable shared CSS to be emitted as a reusable asset, retaining only genuinely small critical styles inline. Measure repeat navigation and first paint afterward. This change concerns stylesheet delivery, not the selected prefetch strategy.

### 8. P2: URL normalization is inconsistent

**Locations:** [current-page comparison](/home/dragos/projects/emdashhq/src/layouts/Base.astro:78), [Hero sheet comparison](/home/dragos/projects/emdashhq/src/components/blocks/Hero.astro:29), [page route](/home/dragos/projects/emdashhq/src/pages/[...slug].astro:8).

The current pathname loses its trailing slash, while menu URLs retain theirs. `/tutorials` does not equal `/tutorials/`, and the descendant comparison appends another slash. All checked menu destinations had no `aria-current="page"`; Hero also cannot find the menu index and falls back to “Cover”.

Additionally, `/tutorials` and `/tutorials/` both return 200 instead of one redirecting. The unslashed route produced a separate 2.51-second MISS even after the slashed route was warm. The canonical tag prefers the slashed URL, but that alone does not unify cache keys or navigation.

**Recommendation:** normalize both menu URLs and current paths consistently, and select one canonical slash policy with redirects. Preserve `/`, handle absolute same-origin URLs deliberately, and apply the same comparison in Hero.

### 9. P2: Site Scripts settings changes have no rendered-page purge path

**Locations:** [Site Scripts hook](/home/dragos/projects/emdashhq/plugins/site-scripts/src/index.ts:98), [cache lifetime](/home/dragos/projects/emdashhq/astro.config.mjs:20), installed EmDash admin plugin-settings handler.

The hook embeds settings into cached HTML. The installed settings-update handler writes options and clears legacy plugin storage, but does not invalidate Astro's rendered-page cache. The plugin also supplies no page dependency or separate invalidation mechanism. Changing an analytics ID, custom HTML, or the master switch therefore does not immediately replace cached output.

**Recommendation:** arrange an explicit public-page purge when these settings change, and connect it to the correct route dependencies. Until that exists, a manual purge is necessary when removing a script urgently. This is established by code inspection; no production settings were changed to test it.

### 10. P2: Every full navigation restarts the hero entrance

**Locations:** [hero content animation](/home/dragos/projects/emdashhq/src/components/blocks/Hero.astro:261), [schematic animation](/home/dragos/projects/emdashhq/src/components/blocks/Hero.astro:615).

Hero text fades in over 0.7 seconds. Schematic labels add staggered delays, with some finishing about 1.7 seconds after the document begins rendering. These run again on ordinary document navigation. They can make an already fast cached response feel slower, independently of server TTFB.

**Recommendation:** keep navigation-critical text immediately readable and limit decorative drawing motion to where it helps. Reduced-motion users already get a complete static hero, which is good. Changing navigation/preload frameworks is not required.

### 11. P2: Shadow tokens contain invalid `light-dark()` values

**Location:** [shadow tokens](/home/dragos/projects/emdashhq/src/styles/theme.css:69).

`--shadow-sm`, `--shadow`, `--shadow-lg`, and `--shadow-xl` wrap entire shadow expressions in `light-dark()`. Chromium rejected the corresponding `box-shadow` syntax; ordinary cards computed to `box-shadow: none`. Other controls use direct shadow declarations, producing inconsistent behavior.

**Recommendation:** use valid values for each property. Given the committed flat Drawing Set instructions, `none` is an appropriate intentional shadow value. If shadows are later explicitly wanted, select valid full shadow expressions through theme selectors, or use `light-dark()` only for supported color arguments.

### 12. P2: Homepage SEO title edits are ignored in `<title>`

**Location:** [Base props on the page route](/home/dragos/projects/emdashhq/src/pages/[...slug].astro:28).

The route computes the homepage SEO object but always passes `undefined` for its title. An administrator's homepage SEO title can therefore affect Open Graph/Twitter output while the browser/search document title remains the site name.

**Recommendation:** honor an explicitly configured homepage SEO title while keeping the site-name fallback for a homepage without an override.

### 13. P2: Mobile navigation has no fallback when JavaScript is unavailable

**Locations:** [toggle handler](/home/dragos/projects/emdashhq/src/layouts/Base.astro:282), [mobile panel styling](/home/dragos/projects/emdashhq/src/layouts/Base.astro:931).

At widths below 900 px, CSS hides the navigation panel. Only JavaScript can reveal it. If the script fails or is unavailable, the visitor cannot access the primary menu. With JavaScript, the menu opens correctly, but the checked Escape key does not close it.

**Recommendation:** make the navigation available by default and apply the collapsed state only after enhancement, or use a native disclosure pattern. Add Escape handling and appropriate focus return. The observed behavior is a disclosure menu, not a modal, so it does not need an unnecessary focus trap.

### 14. P2: Loading an embedded video removes keyboard focus

**Location:** [video replacement](/home/dragos/projects/emdashhq/src/components/VideoFacade.astro:54).

Activating the facade creates an iframe and replaces the focused anchor, but does not move focus to the new player. A keyboard user can lose their position instead of reaching playback controls. This was identified by source inspection; playback was not exercised in the initial browser pass.

**Recommendation:** move focus to the newly attached player when activation came from the keyboard, and preserve modified-click behavior. The existing click-to-load facade, fixed aspect ratio, iframe title, and no-JavaScript watch link are useful practices to keep.

### 15. P3: The architecture illustration labels static values as live measurements

**Location:** [panel footer](/home/dragos/projects/emdashhq/src/components/blocks/Hero.astro:172).

“Live telemetry” and “Edge response: < 20ms” are fixed strings. No telemetry supplies those values. This can mislead visitors, especially when actual navigation is visibly slower.

**Recommendation:** label it as an architecture diagram and remove the unmeasured latency claim, or connect a clearly scoped metric to real measurements.

## Security assessment

No directly exploitable site-specific vulnerability was confirmed in the reviewed scope.

- Production and full dependency audits both reported zero known advisories on this date. This reflects npm's advisory database, not proof that every dependency is vulnerability-free.
- Anonymous plugin-settings and auth requests returned 401 with `Cache-Control: private, no-store`. The admin entry redirected to login. Admin/API responses include a CSP.
- The local plugin-settings API requires `plugins:manage`. Raw custom HTML is deliberately trusted administrator input, as the project instructions specify. Its ability to execute scripts is not, by itself, an unexpected stored-XSS finding.
- Editor-controlled links generally use `sanitizeHref()` through shared helpers. New-tab links receive `noopener noreferrer`; normal textual content is escaped by Astro.
- Public responses include `nosniff`, `SAMEORIGIN`, a referrer policy, and a permissions policy. No public CSP or HSTS header was observed in the sampled responses. Consider these additional protections, with a public CSP designed around existing inline theme code, analytics, media, and intentional administrator scripts. Absence of these headers was not treated as proof of an exploit.
- No `.env`, local database, uploads, or Wrangler state files were found tracked in Git. Secret values were not printed or copied into this report.
- Authenticated cache separation, role changes, actual preview tokens, passkey configuration, secret rotation, and Cloudflare account settings were not exercised. EmDash documents that a logged-in editor can receive an already cached anonymous page because the edge cache runs before the Worker; that limitation should not be confused with a confirmed private-data leak. See [EmDash Cloudflare caching](https://docs.emdashcms.com/deployment/cloudflare/).

## Validation and frontend assessment

- `npm run typecheck`: 31 files, zero errors, warnings, or hints. Wrangler initially encountered a sandbox log-directory restriction; diagnostics still completed.
- `npm run build`: passed after allowing Astro's required local font listener outside the sandbox. The only reported build warning concerned large client chunks, primarily CMS admin assets.
- `npm audit --omit=dev --json` and `npm audit --json`: zero known vulnerabilities.
- Chromium checked all seven public pages at 1440 px and 390 px, exercised a real hover/click, theme switching, and mobile disclosure. No horizontal overflow or browser runtime exceptions were observed in that pass. These checks are not a complete WCAG certification or a slow-device benchmark.
- Fonts are reused from browser cache on later navigations. The first load fetched eight font files, about 141 KB including transfer overhead; this is an initial-load consideration, not an explanation for the measured server delays.
- The Impeccable static detector produced 46 advisory notes and no primary findings. Many notes concern intentional diagram/video colors or display sizes, so they were not promoted automatically into defects. The hand-reviewed implementation does, however, conflict with the documented flat design through actual gradients, lifting interactions, and shadow declarations.

## Suggested implementation order

1. Add list cache hints and error handling, then verify content updates invalidate the homepage and listings.
2. Correct production collection/sitemap routing and consistent slash normalization.
3. Reduce and instrument origin initialization/database work, preserving safe freshness behavior and current hover prefetch.
4. Reuse large CSS assets and make hero text immediately readable.
5. Fix contrast, mobile fallback, video focus, and Site Scripts invalidation.
6. Reconcile valid CSS tokens and measured copy with the committed design.

For frontend follow-up, `$impeccable harden` fits navigation/focus behavior, `$impeccable colorize` fits the contrast corrections, `$impeccable optimize` fits CSS and entrance costs, and `$impeccable polish` can follow the functional fixes. CMS caching and sitemap changes also need the EmDash site workflow. These tasks can be taken individually or together; rerun the relevant checks and `$impeccable audit` after implementation.
